01 Registration

The deadline is enforced by the server, not the browser

Elective registration was a pair of dates on each course offering. That cannot express “this round covers Semester IV of these programmes, opens Monday, closes Friday, and is locked by the coordinator once demand is in”. A round is now a row, and it is the authority.

DRAFTCoordinator attaches courses and sets the window.
OPENStudents may submit and revise preferences.
LOCKEDPreferences frozen. Writes refused.
ALLOCATEDAllocation has run. Results not yet visible.
PUBLISHEDResults released; every student notified.
CLOSEDRound finished.

The student-facing state — NOT_OPEN, OPEN, SUBMITTED, LOCKED, ALLOCATED, CLOSED — is derived, never stored, from the round, the clock and the student’s own rows, so it cannot drift out of step with them.

A countdown in the browser is a courtesy, never a control

Every write calls assert_can_submit(). A stale tab, a clock skewed by a day, or a hand-written request is refused with the real reason. Observed against the seeded database:

OE3 state=LOCKEDPOST /electives/preferences → 409“Preferences are locked while allocation is prepared.”

A round whose closing time has passed refuses writes even while its status still reads OPEN — the deadline wins over the flag.

Eligibility uses the curriculum’s own vocabulary

Rounds narrow by programme, semester and division, so one round can span an Open Elective basket across programmes or narrow to a few divisions of one. Nothing is hard-coded.

Publishing notifies everyone in the round — including students who were not allocated a seat. Silence after a deadline is its own kind of failure.

02 Student profile

Authorised per section, not per endpoint

One view assembling Personal, Academic, Internship, Documents, Evaluation and Mentor. “Staff” is far too wide a rule for a student record: a club administrator has no business reading an internship evaluation, so access is decided section by section.

ViewerResult
The student, their mentor, their department admin, super adminfull profile
An ICT Open Elective coordinatorpersonal + academic only — no evaluation, no mentor
A CSE Summer Internship coordinator403
Club admin · another student403

The response carries visible_sections, so the UI hides a tab the caller may not see rather than rendering an empty one that looks like missing data.

An authorisation flaw a test caught fixed

The first draft granted access to anyone holding a mentor grant for the department. A test asserting that the mentor of student A cannot read student B’s record failed — correctly.

Mentor access is now earned per student: a mentorship assignment, or being the mentor recorded on that student’s own internship.

03 Security

Two real vulnerabilities, both in file access

Unauthenticated document exposure fixed

Uploads were served from a public /media static mount. Every stored document — internship certificates, offer letters, weekly reports — was readable by anyone who knew or guessed its object key, with no login at all.

The mount is gone. Documents reach clients only through an authorised endpoint.

IDOR on file metadata fixed

GET /files/{id} had no authorisation check and returned that public URL. Any signed-in user could walk the id space and collect other students’ certificates. 

intruder  → GET /files/{id}  → 403
owner     → GET /files/{id}  → 200, storage key absent from the body

Also hardened

  • Magic-byte validation. Content-Type comes from the browser and is trivially forged; a “PDF” beginning <script> is now rejected.
  • Filename sanitisation. Path separators, quotes, newlines and control characters are stripped before storage and before being echoed in a Content-Disposition header — a header-injection vector.
  • Signed, expiring links (HMAC, 15 minutes) replace storage URLs, and are issued only after the caller passes the same authorisation check.
  • X-Content-Type-Options: nosniff and Cache-Control: private, no-store on every download.

Verified by 30 API-level tests

Driven through HTTP, because that is where an authorisation gap actually bites: a route that forgot its guard passes every unit test of the logic behind it.

04 Performance

Two N+1 queries, measured then fixed

Measured against the seeded dataset — 1,682 students, 526 courses, 12 curriculum versions — counting SQL statements per request.

EndpointLatencyQueries
Elective components (student) 95 ms→84 ms 221→39
Curriculum explorer (admin) 97 ms→18 ms 70→37
Student dashboard41 ms57
Student profile40 ms39
Student list (paginated)30 ms56
Notifications6 ms4
  1. Scope resolution re-fetched the same rows per offering
    Every offering in a student’s elective list re-resolved the same handful of departments and programmes. Memoised per session — 82% fewer queries.
  2. The curriculum list loaded every component row to count them
    Twelve curricula × ~70 rows, to render six numbers. Replaced with a filtered COUNT — 81% faster.
  3. A third was caught before it shipped
    The round summary loaded every covered student to call len() on them, which timed out on ICT’s cohort. Counting moved into SQL.

No Redis. No caching layer. The queries were the problem; caching them would have hidden it.

05 Database

Six indexes drafted, six removed

Migration 0008_registration_windows adds the rounds table and the foreign key linking offerings to a round. It has been applied and verified to round-trip — downgrade then upgrade — against the live database.

The draft also added six composite indexes for the dashboard queries. Checking 0001 first showed every one of them was redundant:

Drafted indexWhy it was dropped
events(status, start_at)already exists verbatim
notifications(user_id, is_read)exists as ix_notifications_user_read
students.user_idalready unique-indexed by the column’s own constraint
elective_preferences(student_id, component_id)leading column already indexed
elective_allocations(offering_id, status)leading column already indexed
students(department_id, division)leading column already indexed

Redundant indexes cost write throughput and buy nothing. No new indexes were added beyond the new table’s own.

06 API & frontend

Six new routes, three new screens’ worth of work

POST /electives/admin/windowscreate a round — always begins as a draft
PATCH /electives/admin/windows/{id}refused once allocated or published
POST .../{id}/offeringsattach courses — draft only
POST .../{id}/statusdrive the lifecycle; publishing notifies students
GET /student-profile/{id}the unified profile, authorised per section

A pre-existing RBAC gap was closed. Only department admins held electives:manage, so a scoped elective coordinator — plain faculty with a coordinator grant — was locked out of the module they run. The new require_permission_or_coordination guard admits either, and the handler still narrows to the caller’s own department.

Frontend: a tabbed Student Profile page whose tabs are driven by the backend’s visible_sections; the students list now links to it; and the elective workspace reports the backend’s registration decision and its reason rather than computing its own from a countdown. tsc -b clean, production build succeeds.

One trap is called out explicitly. S3_PUBLIC_BASE_URL must be empty for the documents bucket. Setting it makes the backend hand out a CloudFront path instead of an authorised download — re-opening the exact hole Phase 4 closed.

No Kubernetes, no microservices, no Redis. The application is one FastAPI process and one database; an orchestrator would be infrastructure without a problem to solve. Full detail in docs/DEPLOYMENT.md.

09 Status

Do not present this as production-ready

It is a credible MVP with two real vulnerabilities closed and measured performance. It is not yet a system to put in front of a thousand students. Before real use, in order:

  1. Rate limiting on /auth/login
    Nothing throttles password attempts. Add a WAF rate rule at the ALB. future
  2. Malware scanning on uploads
    Type validation and no static serving reduce but do not eliminate the risk. future
  3. A real password policy and reset flow
    Seeded accounts share one password by design — a demo affordance, not a production one.
  4. A browser and accessibility pass
    Not done. No breakpoint audit at 375/768/1024/1440, no screen-reader testing. No WCAG AA claim is made.
  5. A backup restore rehearsal and CloudWatch alarms
    An untested backup is a hope.
  6. A load test at real concurrency
    The dataset has been exercised at 1,682 students; hundreds of simultaneous users have not.

10 Not done

Scope from the brief that this phase did not reach

  1. Event discovery page
    Registration, waitlist and auto-promotion all work and are now tested, but the polished discovery surface — Upcoming / This Week / Registered / Interested / Past with filters — was not built.
  2. Verification queues
    The underlying review endpoints exist and work; the consolidated “Pending Certificates” screens do not.
  3. Audit log filters
    The log is written correctly and is permission-gated; its UI still lacks actor / action / date-range filtering.
  4. Coordinator round-management UI
    The API is complete and tested; a coordinator drives rounds through it, not through a screen. The student side of rounds is wired into the UI.
  5. Systematic responsive and accessibility work
    New pages follow existing patterns — scroll containers on tables, labelled progress bars, semantic headings — but no audit was performed.
  6. Browser-based testing
    Everything was verified through the API and the test suite. The build compiles and types check; the rendered UI was not clicked through.
